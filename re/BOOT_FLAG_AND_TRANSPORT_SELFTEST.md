# Boot flag provenance and transport self-tests

## Observed flag assignment

Read-only instrumentation in tools/trace_boot_flag.py records four zero-byte
initialization writes followed by BFC004FC writing1 to800081F8. No later guest
write changed it in the observed early boot. This is not stale RAM.

BFC004F0 calls BFC00984, which calls BFC0B444 via JALX. BFC0B444 invokes two
tests (BFC0AEF4 and BFC0AFDC). It returns0 only if both return0; otherwise1.
That return is stored in800081F8. BOOTMain at BFC012C6 takes the alternate path
when this value is nonzero, before its BFC03688 channel initialization path.
Calling it a deliberate maintenance/service mode is not yet substantiated;
the confirmed meaning is that at least one of these self-tests failed.

## First test now passes in research execution

BFC0AEF4 uses B00020B4 to select writes/reads and B00020B0 as the data port.
It sends60 repeats of each pattern AAAAAAAA,55555555,FFFFFFFF,00000000,
then checks60 reads for each. B00020B8 bits0/1 are polled before accesses.
B00020BC is written80; its exact hardware semantics are not established.

tools/pace_probe_boot_fifo.py retains the written values in order and returns
them during read mode. It does not inject a test result, boot flag, guest PC
or semaphore value. The first genuine test now returns0 after240 writes and
240 reads. The second genuine test still returns1, so the boot flag remains1.
This is a narrow inferred data-port model, not a complete FIFO specification.

Run: python tools/test_boot_fifo.py; python tools/pace_probe_boot_fifo.py
Evidence: re/boot_fifo_01.json, boot_flag_writes.json, boot_test_a_ghidra.txt,
boot_test_b_ghidra.txt, boot_path_selector_ghidra.txt.

## Second test: transport/demux fixture

BFC0AFDC programs the B000Axxx indexed engine, DMA-related registers and filter
configuration, then waits for indexed register0 to reachB8 and register4 to
reach20B4. Zero-MMIO never does. On success BFC0B194 compares46 words and45
words in RAM against two genuine ROM expected buffers.

Extracted from U202:

| Flash offset | Data |
| --- | --- |
| 1B188 | six188-byte TS packets,1128 bytes total |
| 1B77C | expected buffer0,184 bytes |
| 1B834 | expected buffer1,180 bytes |
| 1B8E8 | first test's four pattern words |

tools/extract_boot_transport_fixture.py assembles PSI sections across packet
boundaries using PUSI pointer fields. The packets alternate PID0/PID1 with
continuity0,1,2. Each PID contains sections of179,35,35,147 bytes. MPEG CRC32
validates all except the second35-byte section, deliberately corrupted in
both PID streams. All table IDs are0; table-id-extension is0 for the179-byte
section and1 for the others.

Both expected buffers reconstruct byte-for-byte from valid sections:

- Buffer0: valid35-byte +147-byte sections with extension1, each followed by00.
- Buffer1:179-byte section with extension0, followed by01.

The trailing00/01 plausibly identifies output/filter, but its meaning needs
register evidence. All section lengths here are3mod4, so the fixture does not
distinguish a one-byte trailer from a more general padding rule. Both PIDs
duplicate the relevant section bytes, so matching output alone cannot resolve
which PID each filter selects. The script reports these ambiguities.

Run: python tools/extract_boot_transport_fixture.py
Evidence: transport_fixture_sections.json, boot_transport_fixture.ts,
transport_test_feed_ghidra.txt, transport_test_check_ghidra.txt,
transport_packet_builder_ghidra.txt (the latter is actually filter-table setup,
not TS packet construction; filename retained as a research-history artifact).
